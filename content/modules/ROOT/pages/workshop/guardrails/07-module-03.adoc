  - name: prompt_injection 
    input: true
    output: false
    detector_params: {}
  - name: language_detection
    input: true
    output: true
    detector_params: {}
  - name: hap 
    input: true
    output: true 
    detector_params: {}
  - name: output_statistics
    input: false 
    output: true
    detector_params:
      custom:    
        - refusal_tracker
routes:
  - name: all
    detectors:
      - regex_competitor
      - prompt_injection

      - hap

== The Reality of having LLMs as judges

**TL;DR** LLMs are highly customsable, but compute intensive.

There are many advantages to using LLMs to judge input and output response. 
They have a stronger semantic understanding and can understand context, intent and paraphrasing better than rules, keyword filters and classifier models. 

They are also very flexible and adaptable since they are prompted, just like we did PeachPal, to look for specific things. 
Updating topics is very easy, and there is often no need to find a specialised model to deploy or retrain it. 

Some downsides are, of course, cost and latency. LLMs are in general larger and more compute intensive than smaller classifier models. 
Currently, there is a lot of research and development using smaller LLMs or quantized version to lower the compute footprint.
There is also a chance to bypass LLM-judges via prompt injection or attacks that attempt to influence judges reasoning or instructions.

LLM-decision may also be harder to trace and explain, especially in compliance-sensitive environments.
