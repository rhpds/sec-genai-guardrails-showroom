Of course! It's the LLM system prompt that we wrote earlier, all laid out bare for the world to see. That's not a good thing.
image:prompt-reveal.png[Revealed prompt]

Getting the LLM to reveal its instructions is a first step to finding deeper exploits and working your way into the system. These type of prompts fall under instruction leakage attacks and one vital part of the defence is not to reveal your policies and instructions to users.


Let's have a look at the second screenshot, at its prompt and at its answer.

Well...it was a nice try of the LLM, but nevertheless, the topic completely derailed from peaches and the user was able to get the information requested. 
This is an instruction override/policy override attack.

Clearly, updating the system prompt alone won't work and we can't use regex since there are many different ways to write a prompt injection. 


We need something that can detect that type of writing pattern and calculate the probability of a prompt belonging to a specific class of prompts.  
We can use a machine learning model trained on prompt injection data.


== Second quest: Enable the Prompt Injection detector

Just like we have Model as a Service providing us sweet access to a LLM that powers PeachPal, so have we guardrail models.
Since the Prompt Injection model is hosted to us, we don't have to deploy it but we can access it via API-calls. 

We call it "Guardrails as a Service" (GaaS, tihi). 
Inside of GaaS, which is running in a separate namespace inaccessible to you, we have several models deployed and waiting to be used. 

We need only to let our TrustyAI instance know where the prompt injection detector is, in what direction it needs to look at the traffic and declare it. 
We need to go to the ConfigMaps and start with the orchestrator.

_You press "ConfigMaps" and then select "fms-orchestr8-config-nlp"._
image:configmap-nlp.png[NLP config]

_You are presented with the following config._ 
image:nlp-config-values.png[Config values]

You can see a couple of things already populated. You see under "openai" the way to the LLM. 
Below it you see "detectors" and there is currently only one defined at the moment which is "regex-competitor". 


We need to give the orchestrator information of where to send traffic to the prompt injection model, so we need to edit this ConfigMap. 

_You press "Actions" and then "Edit ConfigMap"._
image:go-to-edit-nlp-config.png[Edit config]

_You copy the information about where to send the traffic to the prompt injection detector and paste it into the orchestrator ConfigMap. Then hit "Save"._ 

[source,bash,role=execute]
----
passthrough_headers:
  - authorization
tls:
  external_llm:
    insecure: true
    cert_path: /dev/null
chunkers:
  sentence:
    type: sentence
    service:
        hostname: chunker-service.gaas.svc.cluster.local
        port: 8085
openai: 
  service:
    hostname: granite-3-2-8b-instruct-predictor-maas-apicast-production.apps.maas.redhatworkshops.io
    port: 443
    tls: external_llm
detectors:
  regex_competitor:
    type: text_contents
    service:
      hostname: "127.0.0.1"
      port: 8080
    chunker_id: sentence
    default_threshold: 0.5
  prompt_injection:
    type: text_contents
    service:
      hostname: prompt-injection-detector-predictor.gaas.svc.cluster.local
      port: 8000
    chunker_id: sentence
    default_threshold: 0.5
----
_You remove all the existing information and paste the whole chunk. It looks something like this:_
image:add-prompt-injection-nlp.png[Add prompt injection]

Now, we need to tell the gateway about the new detector we added, and at what points it should send the traffic to it.
We go to the other ConfigMap, the one where we added the regex before. 

_You press "ConfigMaps" and thereafter the "fms-orchestr8-config-gateway._
image:config-gateway.png[Gateway config]

_You press "Actions" and "Edit ConfigMap"._
image:edit-regex.png[Edit gateway]

_You copy this whole chunk of text._
[source,bash,role=execute]
----
orchestrator:
  host: "localhost"
  port: 8032
detectors:
  - name: regex_competitor
    input: true
    output: true
    detector_params:
      regex:    
        - (?i)\b(orange|apple|nectarine|plum|apricot|banana|grape|melon|pineapple|lime)s?\b
  - name: prompt_injection 
    input: true
    output: false
    detector_params: {}
routes:
  - name: all
    detectors:
      - regex_competitor
      - prompt_injection
  - name: passthrough
    detectors:
----

_You extend the box, remove all the text and paste the whole new chunk. Then you hit save._
image:edit-config-gateway.png[Edit config gateway]

In this config, we added the prompt injection detector model, we told the gateway to only check on the way in since prompt injection is from user to LLM.
We then added it into the route by name, and in the orchestrator earlier, we added the path to it. Now, TrustyAI knows where to find it.


Remember that the pods of TrustyAI restarts themselves automatically when the ConfigMap is updated, so we don't have to do anything but wait until they are up and running.

_You press "Pods"._

== The Reality of Prompt Injection detections
**TL;DR** Prompt injection hacks are ever evolving, but models are "frozen in time".

Now that we are using models as detectors, specifically, classifiers who look at matching patterns we know that it is only as good as the data it was fed. 

Many of the very "standard" and "common" prompt injection attacks are easily blocked, but the more advanced and not existing in the training data set may still pass. 
Just the same way that the models evolve over time, so does the prompt injection attacks. It is the ever ping-pong match between attacker and defender. 

When choosing your prompt injection model, it is worth to note when it was last updated. A lot can happen in 6-12 months in the prompt hacking field. 
Monitoring the evolution of prompt hacks, and from time having validating checks against the deployed prompt injection model may reveal early where it will fail. 

Better you finding it out then waiting for someone to find out for you.
